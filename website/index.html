What it carries that the others don't

Every design choice is made for a cluster. The speed comes along.

A label on every statement

Cell-level visibility labels, checked on every read, with the same meaning on Accumulo, HBase and RocksDB. Searches and counts honour them too.

Three orders, kept online

Each statement is written to spo, po and osp, so any triple pattern is one range scan. Statistics and an entity index stay current on every write.

One storage interface, three backends

Every call is a native operation of a sorted, distributed store: a range scan, a batch of ranges, a write. Nothing assumes the data fits one machine.

Work moved to the servers

Star intersections and match counts run inside Accumulo's tablet servers and HBase's region servers, so only their results cross the network.

The cost sits on the write side: loading WatDiv took 99 s against 11 s, through the same write path as online updates a 0.99 GB store, between QLever's 0.28 and Oxigraph's 1.22

Three paths

One engine. Three backends. One road to 10¹² triples.

The query engine, statistics and indexes are written once, above a storage interface. Pick the backend that fits: a local directory today, a cluster when the data outgrows it.

Start on one machine

The standalone build is the endpoint and RocksDB in one native executable. It starts in well under a second, needs no JVM and no cluster, and serves the query page with it.

Grow onto a cluster

The same SPARQL, labels and plans on Accumulo or HBase. A bulk build writes each backend's native files and imports them, so a load at scale skips the write path.

Planned for 10¹²

Pre-split tables, server-side intersections and counts, index rebuilds as batch jobs, and planning that reads its statistics in one round trip. The path to a trillion is mapped in the open, item by item.

In the box

A complete SPARQL store, not a prototype.

SPARQL 1.2 and RDF 1.2

Triple terms, reified and annotated statements, and literals with a text direction, on every backend.

Text and GeoSPARQL

text:matches and geof: filters, sped up by optional indexes that honour labels.

Inference at query time

OWL and RDFS rewrites over an ontology loaded in memory, with nothing materialized.

Counts in a few reads

stats:approxSize, stats:approxInstances and stats:approxTriples answer from the statistics.

Every storage call, traced

Add trace= to a request and watch its scans, batches and plan stream live in the query page.

An embeddable Sail

Use it inside your own Java application through RDF4J, or run the standalone SPARQL Protocol endpoint.

Get started

Running in minutes.

Docker brings up the endpoint and its query page. From source you need Java 25 and Maven; the native executable needs GraalVM to build and nothing to run.

With Docker, on RocksDB
# the endpoint and its query page, data kept in a volume
git clone https://github.com/dgreco/tripatha.git
cd tripatha
TRIPATHA_BACKEND=rocksdb docker compose up --build
# then open http://localhost:8080/
From source, as a native executable
# needs GraalVM 25 with native-image to build
mvn -Pnative -pl tripatha.standalone -am package -DskipTests -DskipITs
tripatha.standalone/target/tripatha -Xms4g -Xmx4g \
  --tripatha.backend=rocksdb --tripatha.rocksdb.path=/var/lib/tripatha
Then ask it something
curl -s http://localhost:8080/sparql \
  -H 'Content-Type: application/sparql-query' -H 'Accept: text/tab-separated-values' \
  --data 'PREFIX stats: <urn:tripatha:stats#>
          SELECT ?class ?members WHERE { ?class stats:approxInstances ?members }'
