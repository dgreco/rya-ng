# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Tripatha is an RDF triple store on Accumulo, HBase or an embedded RocksDB database. It's an independent project derived from Apache Rya (see `NOTICE`): a lean Maven build with fourteen modules (plus `tripatha.coverage` under `-Pcoverage`), groupId `org.tripatha`, version `1.0.0-SNAPSHOT`, Java packages under `org.tripatha`. `BACKENDS-STUDY.md` is the design of the storage layer and of the HBase mapping. `SCALE-STUDY.md` drives the work toward 10^12 triples: its tracker (section 2) lists the optimizations (`O…`), measurements (`M…`) and decisions (`D…`). A change that lands one of them updates its row.

| Component | Version | Notes |
|---|---|---|
| Java | 25 | |
| RDF4J | 6.1 | Jakarta-based |

## Build and test

Set `JAVA_HOME` to a JDK 25. If a local path is needed, it's in `CLAUDE.local.md` (git-ignored).

```bash
mvn clean verify                      # everything: *Test (surefire) + *IT on MiniAccumuloCluster (failsafe), ~15 min
mvn test                              # unit tests only, no cluster
mvn -pl tripatha.sail -am install -DskipTests -DskipITs    # failsafe ignores -DskipTests alone

# the store, Sail, loader and endpoint ITs on an in-process HBase cluster instead
mvn verify -pl tripatha.test,tripatha.sail,tripatha.loader,tripatha.sparql -Dtripatha.test.backend=hbase
mvn verify -pl tripatha.test -Dtripatha.test.backend=hbase -Dtripatha.test.hbaseCounters=increment   # counters without the coprocessor

# ...or on RocksDB: no cluster, about two minutes for all of them
mvn verify -pl tripatha.rocksdb,tripatha.test,tripatha.sail,tripatha.loader,tripatha.sparql -Dtripatha.test.backend=rocksdb

# single test: install upstream first, then run one module without -am
mvn -pl tripatha.api test -Dtest=TypeEncodingDelimiterTest
mvn -pl tripatha.sail verify -Dit.test=InferenceIT -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false

# the Spark build's ITs (Accumulo only), and its job jar for spark-submit
mvn -pl tripatha.spark verify -Dit.test=SparkBuildIT
mvn -pl tripatha.spark -am package -DskipTests -DskipITs    # tripatha.spark/target/tripatha.spark-<version>-job.jar
```

- **Naming:** `*Test` = pure unit test, `*IT` = needs a cluster. There is no IT profile; `verify` always runs ITs.
- **Coverage and CI:**
  - `-Pcoverage` attaches JaCoCo's agent to surefire (`target/jacoco.exec`) and failsafe (`target/jacoco-it.exec`). It also adds `tripatha.coverage`, whose `report-aggregate` merges both into `tripatha.coverage/target/site/jacoco-aggregate`.
  - The agent travels in the `argLine` property, so failsafe's `argLine` must keep `@{argLine}`. Any new surefire/failsafe `argLine` must include it too.
  - `.github/workflows/ci.yml` runs `mvn clean verify -Pcoverage` (job `build`), the ITs on HBase in both counter modes (job `hbase`), and the ITs on RocksDB (job `rocksdb`). `.github/scripts/ci_summary.py` turns the test XML and `jacoco.csv` into the run summary and the badge JSON. Each Maven job, the native one included, keeps a Maven cache of its own (`actions/cache`, keyed on the job and the POMs' hash, falling back to the job's previous one): `setup-java`'s single key is saved only by the first job to finish, which left the coverage build fetching JaCoCo from Maven Central every run. `MAVEN_ARGS` makes Maven retry downloads Central rate-limits (429). Pushes to `main` deploy the report to GitHub Pages (`/coverage/`, plus `/badge.json` and `/tests.json`, which feed the README's shields.io endpoint badges).
- **IT base classes** (`tripatha.test`):
  - `StoreITBase` gives each test a `Store` on the backend named by `-Dtripatha.test.backend` (`accumulo` by default; `TestBackends`), and a unique table prefix whose tables are deleted afterwards. `grantAuthorizations(...)` gives the test account labels: Accumulo rejects scans with labels the user lacks and HBase silently ignores them, so any visibility test must call it. `assumeBackend("accumulo")` marks a backend-only test.
  - `TestBackend` is a backend's shared cluster: `openStore()`, `grantLabels`, `compact(table)`, and `storeSettings()`/`endpointProperties()` for code that connects on its own (the loader, the endpoint ITs, `DevServer`).
  - `AccumuloITBase` (a root `AccumuloClient` on the MAC) is for Accumulo-only tests; they run on Accumulo whatever the backend.
  - `tripatha.sail` tests use `RyaSailITBase`, which adds `newConf()`, `newDao(conf)` and `newStore(conf, inference)`.
  - `tripatha.test`'s own tests are the store-level ITs (`RyaStoreDAOIT`, `RangeParityIT`, `LabelParityIT`, `CounterIT`, …), run on the selected backend.
- **The Accumulo test cluster** (`MiniAccumuloSingleton`): one MiniAccumuloCluster per JVM, with `rpc.bind.addr` set to the loopback address. Otherwise its servers advertise the machine's host name, and a name that stops resolving mid-run makes the manager halt the tablet server; the tests then hang until the fork times out. It waits 60 s for its ZooKeeper, not the default 20: where the host name doesn't resolve, ZooKeeper's start-up reverse lookup of an interface address can take 30 s ("Zookeeper did not start within 20 seconds").
- **The RocksDB test backend** (`RocksDBTestBackend`): one database per JVM in a new temporary directory (`-Dtripatha.test.rocksdbPath` names another), kept open until the JVM exits. A shutdown hook then deletes the temporary directory; a named one is kept. The backend has no accounts, so the labels a test grants are only remembered. It is the fastest way to run the ITs while working on anything above the storage SPI; run them on Accumulo and HBase before a PR.
- **The HBase test cluster** (`MiniHBaseSingleton`, recipe in BACKENDS-STUDY.md phase 0): ZooKeeper plus HBase in the test JVM, on the local file system (in-process HDFS clashes with Accumulo's Jersey 3), with `VisibilityController` and `hbase.security.authorization=true`. The process user is an HBase superuser, who sees every cell, so tests run as the normal account `tripathatest`. The coprocessor is on the cluster's classpath through `tripatha.test`'s dependencies. It binds to and advertises the loopback address: with two interfaces on one network, the host name can resolve to the wrong one mid-run. Its data goes under `target/test-data/<id>` (`createRootDir(true)`), which the shutdown hook deletes with `cleanupTestDir()`: a benchmark load leaves about 25 GB otherwise.
- **Speed:** MAC tests cost about 5 s each, mostly creating the six Tripatha tables; HBase tests about the same (table deletes run in the background).
- **Join benchmark** (`JoinBench` in `tripatha.loader`'s test sources, SCALE-STUDY.md M8): `tripatha.loader/bench.sh [--build] [--backend rocksdb|accumulo|hbase] [--profile] [--baseline FILE.csv]`.
  - `--fixed-cost` reports where each query's time goes instead (M14, `FixedCost`): open, parse, prepare, plan with its scans, run, close. `FixedCost` itself runs query files on a copy of a RocksDB store, such as WatDiv's.
  - It loads a generated store of 10M triples once. On RocksDB the store is kept in `tripatha.loader/target/bench/rocksdb` and reused.
    - The store records a finished load itself: the table `bench_loaded` holds the dataset's fingerprint, written after the load's compaction. Deleting the store's directory is all a fresh load needs.
    - A store without that record, or with another dataset, is deleted and loaded again.
  - It runs a fixed query suite and writes a Markdown and a CSV report to `tripatha.loader/target/bench`:
    - latencies;
    - the query thread's CPU time and the JVM's (the rest of a query's time is waiting);
    - scans, cells and storage time from the trace.
  - `--profile` adds where the CPU time goes (CPU samples only).
  - `--entity-index` keeps the entity index (O23): loaded with it, or built on a kept RocksDB store; without it, a kept store's index is dropped. `BENCH_ROCKSDB_PATH` names another RocksDB directory, for a fresh load.
  - Relative paths (`--out`, `--baseline`, `BENCH_ROCKSDB_PATH`) are read from the directory `bench.sh` is run in.
  - It prints the tables' sizes on disk after the load (`TableAdmin.diskUsage`; HBase doesn't report them yet).
  - `--variant NAME:k=v,…` (repeatable) runs each query under each setting, alternating, on the same store, and flags a variant that returns different rows. Runs on different days are too noisy to compare (±40 % on the Accumulo test cluster), so prefer variants.
  - Use `--build` after changing code. Report a query-path optimization as a before/after pair of reports, or as variants of one run when it has a switch.
  - `--bulk` builds the store with the bulk build instead of `load`: a fresh Accumulo or HBase test cluster per run, so a plain run and a `--bulk` run compare the two, and the suite's rows must match.
  - `--write-queries DIR` writes the suite's queries to `DIR/NAME.rq` (CompareBench's form) and stops, without opening a store: the training workload of the native executable's profile-guided build.
- **Engine comparison** (`CompareBench` next to `JoinBench`, SCALE-STUDY.md M11 and section 4.13; setup for macOS and Linux in `tripatha.loader/README.md`): `tripatha.loader/compare.sh [--check] [--build] [--scale 100] [--per-template 5] [--engines tripatha,qlever,oxigraph] [--only a,b]`.
  - **Only a standard benchmark compares Tripatha with other engines:** WatDiv. The join benchmark measures Tripatha's own optimizations, and isn't used for this.
  - It downloads WatDiv v0.6 from the University of Waterloo, checks its SHA-256 and builds it (C++14, Boost). WatDiv publishes no license: never commit its source, model, templates or patches of them. It seeds from the clock, so the data and queries are generated once per scale and kept, under `tripatha.loader/target/compare/watdiv-sf<scale>`.
  - `RdfFileLoad` loads the data into a RocksDB store through the DAO (counters, entity index); QLever builds an index and Oxigraph loads a store from the same file. Tripatha's endpoint (`tripatha.standalone`) serves an APFS clone of its store (a reflink copy on Linux), so the original is never written. QLever and Oxigraph serve read-only, Oxigraph with `--union-default-graph`. All listen on 127.0.0.1 (ports 7101 to 7103).
  - **Tripatha is the endpoint's native executable** (`tripatha.standalone/target/tripatha`), built when it is missing or with `--build`: with Oracle GraalVM the profile-guided build (`build-optimized.sh`, below; `TRIPATHA_PGO=false` turns it off), otherwise the `-Pnative` build as in CI. The report says which, from `target/tripatha.build` when its SHA-256 matches the executable. It runs with `-Xms` equal to `-Xmx` (`TRIPATHA_MIN_HEAP`), and `TRIPATHA_NATIVE` serves another executable, for comparing builds. `--check`, and the start of every run, lists every missing prerequisite (GraalVM 25's native-image, Maven, a C++ compiler, Boost, the word list, QLever) with how to install it.
  - **One engine at a time:** each engine's server is started, measured alone (`CompareBench --raw FILE`), and stopped before the next; then `CompareBench --result FILE …` compares the results and writes the report. Every query is a SPARQL protocol POST whose whole TSV result is read. Each engine first runs every query once, then 3 warm-up and 10 timed runs of each. QLever's result cache is emptied (`?cmd=clear-cache`) before each of its runs.
  - The report first compares the statement counts. A query whose row count differs between engines, or that fails on one, is reported but left out of the geometric means. QLever 0.6.0's `qlever-index` needs `-f -` to read stdin.
  - **Where one query's time goes:** `QueryProfile` (same package) runs one query file in-process on a copy of a RocksDB store, through the Sail as the endpoint does. It prints the plan, the store's scans by reason, the p50 of reading the rows and of writing them as TSV, CPU and GC time, and a JFR CPU profile by area (SCALE-STUDY.md M12, 4.14). `--conf key=value` sets a store setting.
  - QLever comes from its Homebrew tap or its Debian/Ubuntu repository, or `QLEVER_BIN`. Oxigraph is a pinned release, downloaded to `~/.m2/repository/.cache/tripatha-compare` and checked against its SHA-256. To upgrade it, change `OXIGRAPH_VERSION` and the four digests in the script.
- **Hadoop override:** the root POM forces Hadoop 3.5.0 everywhere: Accumulo's default, 3.3.x, fails on JDK 23+ with `getSubject is not supported`, and HBase's 3.4.3 is untested here. `hbase-client` excludes `hadoop-common`/`hadoop-auth` and uses `hadoop-client-api`/`-runtime`, like Accumulo; only the test cluster (`hbase-testing-util`) brings the full Hadoop jars.
- **`metrics-core`:** required at test scope; without it the MAC ZooKeeper dies with `NoClassDefFoundError: com/codahale/metrics/Reservoir`.
- **Logging:** non-Boot modules bind `slf4j-simple` in tests. Do not add it to `tripatha.sparql`, where Spring Boot requires Logback to be the only SLF4J provider.

## Architecture

Data flows `tripatha.api` → `tripatha.store` → `tripatha.sail` → `tripatha.sparql`, with a backend (`tripatha.accumulo`, `tripatha.hbase` or `tripatha.rocksdb`) plugged in under `tripatha.store`. `tripatha.loader` writes through `tripatha.store` only.

### Storage (`tripatha.store`)

The storage SPI (`store.spi`) is cell-shaped: `Store` (`scan`, `batchScan`, `deleteVisible`, `newWriter`, `counterValue`, `countRanges`), `RowMutation` (puts, deletes, counter deltas), `KeyRange` (explicit inclusive flags, and a `Kind` so a backend builds its native range the same way), `ScanSpec` (labels as `Auths`, columns, row and qualifier regexes, a row suffix, a time range, Accumulo-only iterators). The query engine gives the object's type check as a row suffix: RocksDB compares bytes, and Accumulo and HBase filter with `ScanSpec.rowFilterRegex()`, which turns the suffix into a linear expression, `TableAdmin`, `StoreAccess`, `Capabilities`. A backend is a `StoreProvider` found by `ServiceLoader` (`Stores.open(id, settings)`). Everything above it is written once: `RyaStoreDAO`, `RyaStoreQueryEngine`, `RyaStoreEvalStatsDAO`, `GraphSizes`, the indexes and the trace.

`RyaStoreDAO` writes each `RyaStatement` to:
- `<prefix>spo`, `<prefix>po`, `<prefix>osp`: every statement, once per table, so any triple pattern becomes a range scan on one table (`TABLE_LAYOUT`, `TriplePatternStrategy`). The named graph is the column family, the visibility label is the cell visibility.
- `<prefix>eval`: +1/−1 cardinality counters per subject, predicate, object and pair, summed server side by the backend (`EvalStatsMutations` writes `addToCounter` deltas). `RyaStoreEvalStatsDAO` reads them, and they feed RDF4J's join optimizer through `RdfCloudTripleStoreEvaluationStatistics`.
  - **Datatype markers** (`DatatypeMarkers`, SCALE-STUDY.md O14): family `t`, row = predicate, qualifier = the object's datatype IRI, the statement's label, a +1 delta. Every `add` writes them, once per call and key, whether or not statistics are on, before the rows. Only `purge` removes them: `dropGraph` deletes the six counter families only, since a concurrent writer's marker may already be in. Readers that scan `eval` must pick their families.
- `<prefix>graphs`: named-graph markers, used by `getContextIDs()`.
- **Batched adds:** `add(Iterator)` sums the counters of the whole call in a `CounterBatch` (one cell per counter key, drained every 50k keys) and writes each graph marker once per call. The sail adds one statement per call, so this only matters for bulk callers such as the loader. Markers are not cached across calls: `getContextIDs()` deletes markers whose graph has no visible data.
- **Counters of 1:** the planner reads a missing counter as 1, in every branch of `RdfCloudTripleStoreEvaluationStatistics`, so a counter of 1 can be left out.
  - `add(Iterator, CounterPolicy.SKIP_SUBJECT_ONES)` leaves out the `s`, `sp` and `so` cells whose sum for the call is 1.
  - With that policy it holds the whole call's counters, with no early drain. So the call must contain every statement of its subjects.
- `add` is `synchronized`: one DAO serves one writer thread at a time. `setFlush(false)` and `setWriterOptions(...)` (before `init()`) make it a bulk writer.
- Graph IRIs and qualifiers containing U+0000 are refused on every backend (HBase uses that byte to separate column names).
- `<prefix>ns`: namespaces, plus the storage version (row `tripatha`, cf `version`). There is no version triple in SPO.
  - **Version 1.1.0 and the `datatypes` flag** (row `tripatha`, cf `datatypes`) are written only by the `init()` that creates the store: they say every statement has its markers. Older stores keep their version and get no flag, so they are never narrowed. `purge` writes back exactly the version and flag it found.
  - **A DAO refuses to write to a store whose version is newer than its own** (`RyaStoreDAO.isNewer`, number by number): every write method throws, reads work, so an older endpoint can still open it. Raise `RdfCloudTripleStoreConstants.VERSION` when a change makes stores rely on writes older code doesn't make.
- `<prefix>textcount`: the text index's posting counts (O6, SCALE-STUDY.md 4.25), a counter table: row = word `00` predicate, family `n`, the statement's label.
  - **Kept by every write path:** `IndexManager` sums them per write call (`flushCounts`, called by the DAO's `add` and deletes), and the bulk build and `rebuild` sum them in their files. Never through `SecondaryIndex.puts`/`deletes`: O5's replay re-applies those, and counts would double.
  - **Read** by `IndexSearcher`, past its probe, only when the `ns` record `text.counts` holds the text index's definition. It is written with a store created with the index, or by a rebuild that counted (not in HBase's increment mode), and dropped on a redefinition. `query.textcounts=false` turns this off.
  - **Drift:** re-inserts count twice, and graph drops don't adjust them (dropping everything clears them), so `IndexVerifier.verifyTextCounts` reports counts below postings apart from those above them (drift). Below is a bug, every sail test checks it, except through a delete made while a rebuild's sort runs (the job cleared the counts first).
  - **No version bump:** older code doesn't count, but the counts only steer plans. A reader without READ on the table (an Accumulo grant per table) plans as without them (`TextPlanningIT`).
- `<prefix>text`, `<prefix>geo`: optional secondary indexes (`index.text`, `index.geo`), maintained by `IndexManager` in the same writes as spo. Their state (READY/BUILDING plus definition) is in the ns table (row `tripatha`, cf `index`). A store re-reads the states every `index.state.refresh` ms (60,000), on a daemon thread started by its own calls (never on a query thread: it would be in the trace), so readers see an index a loader `rebuild` made READY.
- `<prefix>entity`: the optional entity index (`index.entity`, O23, ARCH.md 13.7), also kept by `IndexManager`: one posting per stored statement, row = shard (`murmur3(subject) mod index.entity.shards`), family = predicate `01` object (as po encodes it), qualifier = subject `01` graph `01` qualifier. Merge joins read stars from it shard by shard when it is READY.
  - **Its matches are answers, not candidates:** a missing or stale posting is a wrong answer. `dropGraph` deletes postings by the graph in their qualifier (the family is the term), and turning it on raises the store to version 1.2.0 so older code refuses to write.
  - **The shard count is in its definition** (a change means a rebuild), and a shard is one row, which no backend splits: about one per 200M triples. A reader that doesn't set it takes the stored one.
  - **By the store** (`Store.intersect`, `Store.canIntersect`): on Accumulo in its servers, by `tripatha.accumulo.iterators`'s `EntityIntersectingIterator`, which leapfrogs each shard's posting lists and returns one key per matching subject with its count (the store asks once per table whether the servers load it); on HBase in its region servers, by `tripatha.hbase.coprocessor`'s `IntersectionEndpoint` (see the HBase backend); on RocksDB with native seeks (`RocksIntersection`). `RyaStoreQueryEngine.entityMatches` calls it for each thread's group of shards when `query.entityindex.servers` is on; otherwise, and where the servers can't, the shards are intersected on the client. Then every star pattern is merged, whatever its length.
  - **Counts:** `SubjectMergeCountOptimizer` (last, only when the store intersects) wraps a group with no `GROUP BY` whose elements are all `COUNT(*)`, `COUNT(?x)` or `COUNT(DISTINCT ?x|*)` over a whole star, or over one star pattern (a class's size: then never with a dataset or `query.limit`), in a `SubjectMergeCount`; `SubjectMergeCountStep` asks `Store.countIntersection` per group of shards, in parallel (Accumulo: the iterator's `count` option, one cell per shard; HBase: the endpoint's count mode, one cell per shard and page). It falls back to RDF4J's group when the subject is bound. `SubjectMergeIT` asserts through the trace that the store counted, so a matcher that never fires can't pass.
  - **Order:** shards are hash partitions, so the threads share one queue, and when a join or OPTIONAL follows, `SubjectMergeStep` sorts the matches by subject in runs (1,024, then up to 262,144): lookups in hash order each read a block of their own. The iterator module depends only on accumulo-core, and the coprocessor module only on hbase-server (provided): keep them so, they are the jars operators deploy. The test clusters' servers get them through `tripatha.test`'s dependencies.
  - Key layout (`IndexKeys`): row = `term-or-cell 0x00 predicate 0x00 subject 0x00 hex(objectHash)`, cf = graph, cq = spo qualifier, and the statement's own visibility and timestamp.
  - Text terms come from `TextAnalyzer` (JDK only). Geo cells are geohash covers from `GeoCells`, with WKT parsed by RDF4J's `SpatialSupport`.

### Backends

- **Accumulo** (`tripatha.accumulo`): `AccumuloStore` makes each SPI call one Accumulo call, built as Tripatha always built it (same `Range`s, iterator names `riq`/`fi`/`ri` and priorities 8/9/11), so traces and behaviour are unchanged. Counter tables get a `SummingCombiner` over decimal text. `AccumuloRdfConfiguration` keeps the Accumulo-only settings (credentials, `setAdditionalIterators`).
- **HBase** (`tripatha.hbase`, BACKENDS-STUDY.md sections 3 and 4):
  - **Cells** (`HBaseCodec`): row = the Tripatha row (the empty row is stored as `00`), one family `c`, qualifier = `family 00 qualifier 00 visibility`, plus the label as HBase cell visibility. The label must be in the qualifier: HBase's key has no visibility, so two labels on one key would collapse, and tags can't be read back. The encoding sorts like Accumulo's keys (`QualifierOrderTest`).
  - **Labels:** "no labels" is sent as the reserved label `tripatha.none`, because HBase reads an empty set as "every label I hold"; "every label held" (`Auths.ALL_HELD`) is sent as no labels. Expressions are parsed by the neutral `VisibilityExpression` and written fully parenthesized. Labels must be registered first (`HBaseLabels`). A store refuses to open if, asking for no labels, it can see a label canary (`tripatha_labels`): its account is a superuser or the cluster doesn't enforce labels. Without the canary table (no `labels` run yet) it only warns.
  - **Reads:** an exact row is a `Get`, a range a `Scan`; `HBaseBatchScan` reads many ranges as one multi-get plus one scan per region (`MultiRowRangeFilter`), in parallel.
  - **Writes:** one `BufferedMutator` per table, all flushed at once; one HBase mutation per operation and label.
  - **Counters:** `coprocessor` mode (default): deltas are plain puts, `tripatha.hbase.coprocessor`'s `CounterObserver` gives each a unique timestamp and sums them on reads, flushes and major compactions. `increment` mode: HBase increments; dropping counters sets them to zero instead of deleting them (an increment's timestamp can run ahead of the clock, and a delete there would hide the next ones). A table's own descriptor decides its mode; an account that can't read descriptors uses its configured mode, so every writer must be configured alike.
  - **Intersections** (D14, SCALE-STUDY.md 4.21): `HBaseStore` attaches `IntersectionEndpoint` to every `INDEX` table it creates. A cluster that can't load the endpoint gets the table without it, and a log line. `canIntersect` calls the endpoint once per table, so an older store's table, or regions without the jar, answer no, and stars are intersected on the client. `HBaseIntersection` asks the region holding each shard row, page after page, with up to `ScanSpec.threads()` pages in flight.
  - **Counts** (O26, SCALE-STUDY.md 4.22): `RangeCountEndpoint` goes on every `STATEMENTS` table, with the same fallback and a probe of its own (`countsWithoutReading`): an older jar intersects but doesn't count. `-Dtripatha.test.hbaseIntersectPage=N` also ends its pages after N rows.
    - **Labels:** a scanner an endpoint opens skips the region's coprocessor hooks, and with them `VisibilityController`'s filter. So the endpoint runs the region's `preScannerOpen` on each of its scans, on the call's thread, and the caller's labels apply as on a client scan. `HBaseIntersectionIT` checks labels the account doesn't hold.
    - **Pages** (`Leapfrog`): a page ends after a number of matches, cells read or milliseconds, always between two subjects, and says where the next one starts. The limits are `tripatha.intersect.page.*` in the client configuration, or the endpoint's defaults.
      - Every cell the scanner examines spends the budget, hidden ones included. That is why the endpoint's own filter applies the time range.
      - A paused list reopens at the cell it stopped at. The cell a reopened scanner seeks past isn't charged: an allowance of one cell would otherwise never reach the next cell.
      - After a seek a list reads one cell, doubling while it is read in order: a full batch after each seek reads cells the next seek skips.
      - `LeapfrogTest` checks pages of every size against a plain intersection. Run the ITs with `-Dtripatha.test.hbaseIntersectPage=1` to end every page after one match and one cell.
    - **The protocol** (`src/main/proto/entity_intersection.proto`) is compiled to Java once and checked in. HBase 3.0 runs endpoints on its shaded protobuf 4.34.0, which refuses newer generated code. So `generate-protos.sh` uses protoc 34.0, from Maven Central and pinned per platform by SHA-256, and moves the output to the shaded package. Run it after changing the `.proto`; `--check` says whether the checked-in code is current. Upgrading HBase may need another protoc, matching its runtime.
  - Rows over 32,767 bytes are refused.
- **RocksDB** (`tripatha.rocksdb`, BACKENDS-STUDY.md section 10): a store in a local directory, in the caller's process.
  - **Cells** (`RocksCodec`): key = `esc(row) 00 01 family 00 qualifier 00 visibility`, where `esc` writes a `00` byte as `00 FF`, so RocksDB's default byte order is Accumulo's key order (`RocksCodecTest`). Don't give RocksDB a Java comparator: it costs a JNI call per comparison. Value = 8-byte big-endian timestamp, then the value. One version per cell: the last write wins.
  - **Tables** are column families of one database; a table's `TableKind` is recorded in the default column family. Every family has the add operator, so the database reopens without knowing each kind. `deleteRows` drops and recreates the family; handles of dropped families are closed with the database, because a scanner may still be reading one.
  - **Labels** are enforced in `RocksScan` and `RocksIntersection`, the only read paths, with `VisibilityExpression`. There are no accounts: every label is held, `Auths.ALL_HELD` filters nothing, and `heldLabels()` is empty. File access to the directory bypasses labels.
  - **Counters:** RocksDB's `uint64add` merge operator, 8-byte little-endian, summed on reads and compactions. Merging onto a value that isn't 8 bytes silently restarts the count, so counter tables refuse PUT and other tables refuse counter deltas.
  - **Counts** (`RocksCount`, O26): `countRanges` reads each range's keys with native iteration, builds no cell, finds a key's graph and label from its end (a forward parse of `spo`'s long rows took 62 % of WatDiv C3's CPU), and reads a value only for a time range. Row and qualifier filters go to the scanning default.
  - **Writes:** one `WriteBatch` per `CellWriter`, across families; a flush is one atomic write. A timestamped delete first writes the batch, then reads the cell and deletes it only if its timestamp is at or before the delete's.
  - **One database per directory and process** (`RocksDatabase`): stores and scanners of a directory in one JVM share the open database and count their uses; the last release closes it. Scanners hold native memory: close them (they close themselves when exhausted).
- **Bulk imports (M6, SCALE-STUDY.md 4.17):** `AccumuloBulkSpikeIT` and `HBaseBulkSpikeIT` (`tripatha.test`, each on its own backend) and `RocksBulkSpikeTest` (`tripatha.rocksdb`) write files in the backend's native format with its own codec (RFiles, SST files with `merge` entries for counters, HFiles whose visibility tags hold label ordinals from `hbase:labels`), import them into tables that hold data, and read them back under labels. They pin what the bulk build (O3, O10) relies on:
  - Accumulo and RocksDB add imported counters to what is there;
  - HBase adds them only with a timestamp per import in coprocessor mode, and replaces or hides them in increment mode;
  - importing again counts again, or not at all.
- **Trace:** `StoreTrace` (scope, reasons, `Trace`) is neutral, and every backend reports the same way: reads through `TracedScans.open`, visible-cell deletes through `TracedScans.started`, writers with `trace.wrote` and `trace.flushed`. Only the operation names and the filter list are a backend's own. Accumulo lists the scan iterators it attaches (`AccumuloStore.iterators` builds them, `describe` renders them), so add a new server-side filter there and it shows in traces. What is done directly with `AccumuloStore.client()` is not traced.

### Loader (`tripatha.loader`)

A command-line stress loader (`LoaderMain`: `dry-run`, `prepare`, `load`, `build`, `rebuild`, `verify`, `drop`, `check`, `labels`), packaged as a Boot executable jar and run with `tripatha.loader/run.sh`.
- **Generator** (`gen/`): `EntityGenerator.generate(i)` returns entity `i`'s statements from the seed and `i` alone (`SplitMix64` streams), so any process can produce any range, and a rerun writes identical keys (one fixed timestamp per dataset). `ClassLayout` interleaves the classes over 1000 slots. Literals use the exact lexical form the resolvers read back. `GenConfig.fingerprint()` identifies a dataset. `--rdf12-fraction` annotates that share of the links with triple terms and gives that share of the language-tagged labels a base direction, from a random stream of its own: the other choices, and the fingerprint at 0, are those of the RDF 1.1 dataset.
- **`prepare`** runs once, from one process: one DAO init creates the tables with READY indexes (concurrent inits would race), `SplitPlanner` adds split points at quantiles of the rows a sample would write (same serializers as the DAO), and `ReferenceData` writes the ontology plus the dataset description holding the fingerprint.
  - **How many splits** (O2): by default each table's estimated size on disk (`SplitPlanner.Sample.diskBytes`: a 5,000-entity sample's cell bytes, scaled, over `--compression`, 7) over `--tablet-size` (10G), at least `4 × servers − 1`. `--splits N` asks for N everywhere. `SplitPlannerTest` checks that 1T plans about the 2,100 tablets per statement table of SCALE-STUDY.md 4.4.
  - **`TableAdmin.setTargetSize`** then makes `--tablet-size` the backend's own split threshold: Accumulo's `table.split.threshold`, HBase's `MAX_FILESIZE`, a no-op on RocksDB.
  - **HBase splits in rounds** (`HBaseStore`'s `addSplits`): each round splits every region holding planned points at its middle one, at once, so n points take about log2(n) waits. A region split from one with data refers to its parent's files and can't split again until a compaction: a round where none split compacts the table and retries, up to 10 minutes. Empty tables, as before a load, never need that. `TableAdminIT` covers both on every backend.
- **`load`:** `StoreCheck.forLoad` refuses a store that wasn't prepared for the same dataset and index settings. Each worker thread has its own DAO, claims blocks of entities from a shared cursor, and writes each block with one `add`. A block is recorded in the `Progress` file only after a later flush; `--resume` skips recorded blocks. The file is a watermark plus the blocks done above it (blocks are claimed in order), a few bytes at any size, under the key `load`; the earlier bit-set form (key `fingerprint`) is read and rewritten, and older loaders refuse the new one rather than reload and double the counters.
- **`build`** (O3, SCALE-STUDY.md 6.2, 4.18 and 4.19): the bulk build, on backends whose `Store.bulk()` is present (RocksDB and Accumulo; HBase with O10).
  - **Sort:** each worker writes its blocks with its own DAO over a `CapturingStore`, which sends the bulk tables' writes (`spo`, `po`, `osp`, `eval`, `text`, `geo`, `entity`) to a `SpillBuffer` and the rest (`ns`, `graphs`) to the store. So every cell is the one `load` writes.
  - **Spills** are sorted RFiles per table (`Spills`, read without Accumulo's iterators, used for sorting only). They are recorded with their blocks in one `Progress` commit, and a worker's update of the shared run list happens in that same lock: otherwise another worker could record a run whose blocks aren't recorded. Unlisted runs are deleted on resume. A worker merges its runs of a table past `FAN_IN` (64).
  - **Merge:** per table and per row range. The ranges are fixed in `merge-plan.properties` the first time: split rows change as files are imported, and a range merged twice would be imported twice. Counter totals of 1 are left out only in the six counter families, never `p` and never the datatype markers (a missing marker is a wrong answer).
  - **Import:** each file once, recorded, and a file that is gone was imported.
  - **HBase** (`tripatha.hbase.bulk`, a module of its own: it needs hbase-server, with Hadoop and the web stack excluded so the shaded Hadoop client stays the only one; `HBaseStore.bulk()` finds it with `ServiceLoader`, so the endpoint never loads it). `HBaseBulkImport` writes HFiles through `HBaseCodec`, with the column family's settings and visibility tags of label ordinals, and loads them with `BulkLoadHFiles` as the store's user.
    - **Ordinals:** HBase shows `hbase:labels` to superusers only, and the loader's account isn't one. So `HBaseLabels.writeCanaries` (the `labels` command, as a superuser) stores each label's ordinal in its canary, and `HBaseLabels.ordinals` reads those of the labels the account holds. A label without one stops the build.
    - **Counters:** in coprocessor mode, stamped with the build's own timestamp. A work directory left by another build is refused, so that timestamp isn't reused and cells don't collapse. In increment mode, `refusesCounters` stops the build (decided 2026-11-20).
  - **Accumulo** (`AccumuloBulkImport`): RFiles written with the table's own configuration, counters as decimal text for its combiner, imported per table with a `LoadPlan` naming each file's rows. A split point ends its tablet there (`BulkImport.splitPointEndsTablet`), so a file covers `(previous, point]`; elsewhere `[previous, point)`. Either way each file falls in one tablet.
  - **Tests:** `LoaderIT`'s `aBuild*` tests compare it with `load` cell by cell, and cover a crash and resume. They run where counters can be imported; `aBuildIsRefusedWhereCountersCantBeImported` covers HBase's increment mode. `LoaderIT` passes the test cluster's counter mode to the loader (`--hbase-counters`). `HBaseBulkImportIT` (`tripatha.test`) covers HBase's files as the normal account.
- **`rebuild`** (O5, SCALE-STUDY.md 4.23; `IndexRebuild`): builds a store's indexes that aren't READY, any store, as a batch job. Phases `start,sort,merge,import,finish`, each resumable; the merge and import are `BulkFiles`, shared with `build`.
  - **Start:** a DAO opened with `index.rebuild.job` marks the indexes BUILDING for the job (clearing a redefined one), records the job in `ns` (row `tripatha`, cf `index`, cq `job`), and raises the store to version 1.3.0 (`VERSION_WITH_REBUILD_JOBS`): older writers record nothing.
  - **Sort:** `spo`'s split ranges (fixed in `rebuild-plan.properties`), read with `Auths.ALL_HELD`; each range's runs and row sample are recorded in one `Progress` commit. **Merge:** the index tables are split from the samples first (on RocksDB as hints, at least one range per thread).
  - **Deletes during the job:** `RyaStoreDAO.deleteMatches` records each deleted `spo` cell in `ns` (`RebuildLog`) and flushes before deleting, while an index is BUILDING. `finish` deletes the index cells of recorded cells gone from `spo` (at their timestamp), writes again those still there (an import may have replaced them with an older version), then repeats the delete half for cells recorded during that pass. Never write index cells in the second pass.
  - **Refused while a job runs** (`IndexManager.refuseWhileRebuilding`, read afresh): `dropGraph`, `purge`, `rebuildIndexes`; a start-up with `index.rebuild=true` leaves the indexes to the job. A DAO whose definition of an index differs from the stored one is refused instead of clearing the table, the job's own resume included.
  - `LoaderIT`'s `aRebuild*` tests cover it on every backend, both HBase counter modes included: the replay test compacts the index tables before the import so the deleted postings really come back on Accumulo and HBase, and checks they did; `RebuildBench` (test sources) times it against the start-up rebuild.
- **Subject counters of 1:** by default (`--stats-ones skip`, a dataset option) each block's add leaves them out.
  - This is exact because no subject appears in two entities, or in an entity and the reference data. `EntityGeneratorTest` guards that.
  - A generator change that breaks it must also change this.
- **Connection:** `StoreFactory` opens `--backend accumulo|hbase|rocksdb`. RocksDB needs only `--rocksdb-path DIR` (or `TRIPATHA_ROCKSDB_PATH`), which also selects it; `prepare` plans no splits for it, and one process at a time can open the directory (`--threads`, not `--part` across processes). For Accumulo, `ClientFactory` uses `AccumuloClients.fromFile` (in `tripatha.accumulo`, shared with the endpoint); a properties file with password auth and no `auth.token` takes the password from `TRIPATHA_ACCUMULO_PASSWORD`. For HBase, `LoaderOptions.hbaseSettings()` layers the provider's settings: `TRIPATHA_HBASE_*`, then the `--hbase-properties` file (which selects HBase; only provider keys, client settings as `hbase.conf.<key>`), then `--hbase-site`, `--hbase-conf 'k=v;k=v'`, `--hbase-user`, `--hbase-counters`, `--hbase-counters-jar`. An empty `--hbase-user=` clears the account, so `labels` can run as the process user. `check` reports what the store reaches. An account that sees label canaries (`HBaseLabels.NotEnforced`) is a configuration error, exit 2.
- **`labels`** (and `prepare --grant-auths`) gives an account labels; on HBase it also registers them, grants `tripatha.none`, and writes their canaries (needs an HBase superuser).
- **`configure.sh`** asks for the backend first, then writes `accumulo-client.properties` or `hbase.properties` (for `--hbase-properties`), with mode 600. For RocksDB it writes nothing: it asks for the directory and prints the `--rocksdb-path` option. Test it as `/bin/bash tripatha.loader/configure.sh` with piped answers and `--defaults` for both backends. Values are escaped the way Java reads `.properties` (ISO-8859-1): anything outside printable ASCII becomes `\uXXXX` via `iconv` and `od`, which must stay bash-3.2 compatible.
- **`verify`** regenerates a sample of entities and compares them with spo and the subject counters, under the reader's labels.
- `LoaderIT` checks spo and eval cell by cell against the regenerated data, after parallel parts, a stop and resume, and a write failure followed by a resume.

### Spark build (`tripatha.spark`)

The bulk build as a Spark job, for Accumulo (SCALE-STUDY.md O28, D5 (b), section 4.28; how to run it in `tripatha.spark/README.md`). `SparkBuild` (commands `generate`, `files`, `smoke`) runs under `spark-submit` with the module's shaded jar (classifier `job`), on Spark 4.2 and Java 25. Its own options are parsed first; the rest are the loader's, parsed by `LoaderOptions` as for `build`.
- **Dependencies:** it depends on the loader's classes through `tripatha.loader`'s `lib` jar (the main one is Boot's executable), without HBase, RocksDB or `slf4j-simple`.
  - Spark, Scala, Hadoop, ZooKeeper, Netty, Jackson 2 and the logging are provided, and left out of the job jar: they are the cluster's.
  - Thrift, Guava, Gson, Protobuf and Caffeine are relocated under `org.tripatha.shaded`. Spark 4.2.1's jars carry Thrift 0.16 against Accumulo's 0.24, and other Guava and Gson versions.
- **Cells:** `CellMaker` runs a `RyaStoreDAO` over a `CapturingStore` of an `EmptyStore`, so every cell is the one `load` writes.
  - The `EmptyStore` must have the real store's tables (`JobSpec.existing`): a DAO refuses an index table its settings don't enable.
  - Every task parses the loader's arguments again (`JobSpec.options()`), with a size in triples given as entities.
- **Layout** (`Shuffle.Layout`): one Spark partition per file.
  - **Points:** each table's tablet split rows, plus sample quantiles within each tablet, for files of about `--file-size` (at most 50 per tablet). A point ends its range, as on Accumulo.
  - **The entity index's shard rows** are spread over `buckets` files by column hash; files of one tablet may overlap.
- **Shuffle:** a task adds up its counters across write calls (`Tasks.COUNTERS` keys), and `repartitionAndSortWithinPartitions` sorts each partition in Accumulo's key order. `Tasks.write` adds up equal keys and keeps the newest put, as `Shuffle.Value.combine` decides (deterministic, so a task run twice writes the same file). Spark's own combining (`ShuffledRDD` with an aggregator) hashed every cell and was 1.6 times slower: don't bring it back.
- **Counters left out:** `BulkBuild.leftOut`, shared with the loader, with `SKIP_SUBJECT_ONES` only when the totals are the store's: a generated dataset, or files into a new store (`job.properties` `fresh`). With `--append` only zeros.
- **Work directory** (`WorkDir`, any Hadoop file system): it must be on one of Accumulo's volumes, or the import is refused.
  - `job.properties`: the input's fingerprint, the timestamp, and the state `writing`, `written`, `importing` or `done`.
  - `files/<table>/NNNNNN.rf`, and `manifest.properties` (each file's rows, for the load plan).
  - **Rules:** a write deletes `files` and starts over, and is refused once an import started. The import skips files that are gone (imported), and refuses a table directory still holding `loadmap.json`, because Accumulo 2.1.6 doesn't check it.
- **Files** (`RdfLines`, `Tasks.LineBatches`): `TextInputFormat` splits, parsed `CHUNK` lines per RDF4J call, line by line only for a chunk that fails.
  - **Blank nodes:** kept (`PRESERVE_BNODE_IDS`) and prefixed with the file's id (`RdfLines.fileId`: path, length, modification time).
  - **Statements** get the job's timestamp and `--visibility`.
  - **Bad lines:** a statement the DAO refuses is retried alone, and the `CellMaker` reopened after a failure. Both kinds count toward `--max-bad-lines`.
  - **`--distinct`:** `distinct()` over the spo cells (`Tasks.Bytes`), then `deserializeTriple`.
- **Kryo:** everything that crosses a shuffle or a task result is a plain class with a no-argument constructor (`Shuffle.Key`, `Shuffle.Value`, `Tasks.FileWritten`, `Smoke.Result`), never a record or an immutable `List.of`.
- **Tests:** `SparkBuildIT` (local Spark and the Accumulo test cluster; skipped on the other backends) compares `generate` with the loader's `build`, and `files` with a DAO load of the same statements, cell by cell. `SparkJava25SpikeTest` runs Tripatha's encoding in Spark tasks. The surefire and failsafe `argLine`s add the JVM options Spark's launcher adds (`spark.test.jvm` in the module's pom). `LocalCluster` (test sources) runs a throwaway Accumulo for trying `spark-submit` on one machine.

### Row encoding (`tripatha.api` `resolver`)

- Row = s `0x00` p `0x00` objData `0x01` marker (column order differs per table).
- Values are encoded by mango `LexiTypeEncoders`, one resolver per datatype (marker bytes in the `*RyaTypeResolver` classes; `xsd:int`=13 and `xsd:integer`=5 are separate).
- **RDF 1.2:** a triple term is a `RyaTripleTerm` (reserved datatype `RyaSchema.TRIPLE_TERM`, marker 14, `TripleTermResolver`): `02 esc(s) 02 esc(p) 02 esc(o with its own marker)`, objects only, nested by applying the layout again. A literal with a base direction is an `rdf:dirLangString` whose language field is `ar--rtl`, stored by `CustomDatatypeResolver`.
- `EncodingCompatibilityTest` pins the bytes of every resolver and row layout. A change that makes it fail changes what existing stores hold.
- **The hashed row layout (`tbl.hashprefix`, `WholeRowHashedTripleResolver`) is deprecated** (O9, SCALE-STUDY.md 5.3): it spreads no hot key and costs 33 B per row. Keep it working for the stores on it; don't build new features for it (graph sizes and merge joins refuse it).
- **Encoded values must never contain `0x00`/`0x01`.** `RyaTypeResolverImpl.checkNoReservedBytes` enforces this, and `TypeEncodingDelimiterTest` guards it. Do not switch to Accumulo lexicoders: they emit raw bytes.

### Query path (`tripatha.sail`)

- **Connection:** `RdfCloudTripleStoreConnection.evaluateInternal` uses RDF4J's stock `DefaultEvaluationStrategy`, subclassed as `RyaEvaluationStrategy`, over `StoreTripleSource`.
- **Optimizers:** `RyaQueryOptimizerPipeline` mirrors RDF4J's `StandardQueryOptimizerPipeline`, with `InferenceOptimizer` (the 15 `*Visitor` rewrites in `inference/`) inserted before `QueryJoinOptimizer`.
  - **Planning's counter reads together** (O27, SCALE-STUDY.md 4.26): after the index search and before the value ranges and join ordering, `RdfCloudTripleStoreEvaluationStatistics.prefetch` reads every pattern's counter in one batch (`getCardinalities`). The estimates then read that per-query map; `query.stats.prefetch=false` turns it off.
  - **Keep the two agreeing:** the estimate and the prefetch pick a pattern's counter through the same `counterRead`. A new estimate path must use it, or its reads go back to one round trip each (`PlanningReadsIT` counts them). When copying RDF4J internals, read the sources jars in `~/.m2` (for example `rdf4j-queryalgebra-model-6.1.0-sources.jar`).
- **Join shape:** RDF4J's join optimizer nests joins to the right (`Join(a, Join(b, c))`), which evaluates the inner join once per row of `a`: nothing to batch, no entity chain. `LeftDeepJoinOptimizer`, the last step of the pipeline, rotates them to `Join(Join(a, b), c)`, same argument order and same results. It leaves merge joins, scope changes, subqueries and join subclasses (inference) alone.
- **Batched joins:** `RyaEvaluationStrategy.prepare(Join)` returns a `BatchedJoinStep` when the right side is a plain statement pattern, optionally under filters, and there is no dataset, merge join, scope change or `query.limit`. Otherwise it uses RDF4J's own join.
  - The step reads left rows in windows (64, doubling up to `query.join.batchsize`, default 1000), and `StoreTripleSource.prefetch` fetches all of a window's lookups via `BatchLookup` (one `batchQuery` per table and graph). A `LIMIT` query thus stops after a small fetch.
  - RDF4J's own statement-pattern step then runs per row against that cache, so join semantics stay RDF4J's.
  - `BatchLookup` matches results to lookups on exact encoded values and deduplicates cells. A key's range is its bound parts in the table's order, each followed by a delimiter, so two ranges overlap only when one key's parts are a strict prefix of another's (`(s, p, ?)` and `(s, p, o)`). A group without such a pair is disjoint and skips the deduplication (O17), and the objects' encoding when no key binds one. Anything that changes how ranges are built must keep this true, or bring the check back.
  - **Threads (O16):** such a group is also read in chunks on up to `query.join.lookupthreads` threads (unset, `Capabilities.lookupThreads()`: 4 on RocksDB, 1 on Accumulo and HBase; endpoint `tripatha.join-lookup-threads`), each with at least `query.join.lookupthreadkeys` lookups (256). A group keeps one pattern per range (its bound parts in the table's order), so no range is read twice: two keys of one range, differing only in an object's type or in their graph condition, would otherwise land in two chunks, and a repeated key gives its cells twice. The query thread reads the first chunk, joins every chunk before returning or throwing (no scan may outlive `fetch`), and counts the prefetch limit across them. A thread that joins another's trace keeps its reasons to itself (`StoreTrace.reason`), since the trace's stack is the query thread's. Run the ITs with `-Dtripatha.test.lookupThreads=3` to read every disjoint batch on three threads. Never register a partial prefetch: a missing key must mean "ask the store".
  - **Subject ranges** (`query.join.subjectranges`, off by default): a subject asked for by two or more keys of a batch in `spo` is read as its whole range, and the exact matching keeps the answers.
    - If those ranges return more than 64 cells per subject (plus 1,024), the batch is re-read one range per key.
    - It is off because on the warm benchmark it read 4× the cells for no gain. It is to be tried on a cold cache.
  - Run the ITs with `-Dtripatha.test.joinBatchSize=2` (and `-Dtripatha.join-batch-size=2` for `tripatha.sparql`) to push every test through chunk boundaries.
  - Run them with `-Dtripatha.test.indexes=true` to maintain the text, geo and entity indexes in every test. `RyaSailITBase` then checks each test's index tables against spo with `IndexVerifier`. A test that loops over `IndexType.values()` must skip the indexes it didn't enable.
- **Counted patterns** (O26, SCALE-STUDY.md 4.22): a pattern whose object variable no other part of the query names (`?f` in `SELECT ?p WHERE { ?p a :Person ; :knows ?f }`) only decides how many times each row comes back. Its lookups ask the store how many statements match, instead of reading and decoding them, and each row is repeated that many times. On by default (`query.join.countunused`, endpoint `tripatha.join-count-unused`).
  - **Which patterns** (`CountedPatternOptimizer`, the last optimizer): a plain pattern on the right of a join or an OPTIONAL, alone or under filters, whose object no pattern, filter, `BIND`, `VALUES`, projection, grouping, ordering, subquery or outside binding names. It marks none in a query with `COUNT(DISTINCT *)` (which tells rows apart by every variable), `DESCRIBE`, a `SERVICE`, a dataset or `query.limit`. Names are counted over the whole query, every scope included.
    - A name can be held as a string as well as a `Var`: `ProjectionElem`, `ExtensionElem`, `Group`, `GroupElem` and `BindingSetAssignment` names count.
    - A new node type with variables must visit them in `visitChildren`, or a pattern whose object it uses gets counted.
  - **The rows** (`CountedPattern`, `CountedPatternStep`): a row is counted when its subject, predicate and any graph are bound and its object isn't. Otherwise it is looked up as before: an unbound graph (`GRAPH ?g`), the default graph alone, or an object bound from outside. The repeated row is the same binding set each time: RDF4J's steps copy a row before adding to it.
  - **Batches:** `BatchedJoinStep` and `EntityPrefetchStep` put a counted pattern's keys in the same batch as the others' (`StoreTripleSource.Batch` holds statements and counts), so the release rule and fetching ahead apply unchanged. `BatchLookup.count` groups the keys by table, graph and length, so a call's ranges can't overlap, and counts large groups in chunks on the lookup threads, as a disjoint group is read.
  - **Counted apart only where it saves the read** (`Store.countsWithoutReading`: RocksDB, Accumulo when its servers load the counting iterator, and HBase when a table's regions answer the count endpoint). Then the count runs on a lookup thread while the window's statements are read (`BatchLookup.fetchAndCount`), so it costs a round trip but no wait. Elsewhere a window's counted keys are fetched with its other keys, in the same scans, and counted from their lists. A count of its own there is a second round trip for the same cells: `star-unused` was 91 % slower on Accumulo and 53 % on HBase. A row no batch counted goes to RDF4J's step on those stores.
  - **Counts by the store:** `RyaQueryEngine.countBatch` builds the ranges and spec a lookup would, and `Store.countRanges` counts them. The ranges must not overlap.
    - The SPI's default batch-scans them and counts each cell in the range holding its row (`RangeCounts`).
    - RocksDB counts with native iteration (`RocksCount`): each key read once, its family and label found from its end, its value read only for a time range.
    - Accumulo counts in its tablet servers (`RangeCountingIterator`, in the iterator jar): one entry per range and tablet, at the range's **last** key, so a scan the server resumes after it counts nothing twice. A range across tablets gives one count per tablet, added up by the client. The store asks once per table whether the servers load it.
    - HBase counts in its region servers (`RangeCountEndpoint`, attached to every statement table; `HBaseRangeCount` on the client): one call per region and page, the regions asked at once. Each range is counted inside the region only, and the client queues every part a region didn't count (past its end, before its start, after its page) for the next round. A page ends between rows; a row filter that sees hidden rows too keeps its budget.
  - **Tests:**
    - `CountedPatternIT` runs every query with counts on and off, with and without a label, and checks through the trace which ones count.
    - `CountedPatternOptimizerTest` covers the ways a name can be used.
    - `CountRangesIT` (`tripatha.test`) compares counts with scans on every backend: labels, graphs, a time range, ranges across splits, a scan batch of two cells.
    - `-Dtripatha.test.countUnused=false` runs every sail test without counts.
- **Entity prefetch:** `prepare(Join)` (before trying a `BatchedJoinStep`) and `prepare(LeftJoin)` look for an `EntityChain`: joins and OPTIONALs that each add one statement pattern over a driver, typically an entity's attributes (`?s a :P ; :name ?n OPTIONAL { ?s :email ?e }`). On by default (`query.join.entityprefetch`, endpoint `tripatha.entity-prefetch`); needs batching allowed.
  - A link qualifies if its subject or object is bound on every driver row, and it uses no variable bound by a link below it (unless the driver binds it on every row). A join with a filtered pattern stays in the driver. A chain needs two links or one OPTIONAL; a single join is `BatchedJoinStep`'s job.
  - `EntityPrefetchStep` reads driver rows in windows (64, doubling up to the batch size), fetches every link's lookups for the window in one `StoreTripleSource.prefetch`, and releases them when the next window is read. A window over `query.join.prefetchlimit` is halved; one row still over it goes to the store.
  - **Fetching ahead** (O16, `query.join.prefetchahead`; unset, on where `Capabilities.lookupThreads()` is over 1, that is RocksDB; endpoint `tripatha.join-prefetch-ahead`): from the second window on, the next window's rows are read as soon as the current one is handed on, and their keys built and lookups fetched on another thread (`StoreTripleSource.fetch`). Only the query thread holds a batch (`hold`), when it moves to that window, so the release rule above still holds; closing the step waits for a fetch still running. `-Dtripatha.test.prefetchAhead=true` turns it on for the ITs on any backend.
  - The links are RDF4J's own nested loops (`JoinIterator`, `LeftJoinQueryEvaluationStep`), never `super.prepare(Join)`, which may pick a join that doesn't look up per row. They ask for the next driver row only after the current one's lookups are done, which is what makes the release safe; a miss only costs a store lookup.
  - Patterns rewritten by inference (subPropertyOf, inverseOf, …) end the chain; an inferred type can still be its driver.
- **Merge joins** (O22, ARCH.md 13.6): a star of constant patterns (`?x a :P ; :worksFor :Acme ; :nationality :IT`) can be read as subject-sorted `po` ranges and intersected, instead of one lookup per driver row.
  - **Where:** `SubjectMergeOptimizer`, the last optimizer, finds a left-deep chain of plain joins whose driver is a star pattern on `?x`. A star pattern is a plain `StatementPattern` in the default scope with a variable subject, a constant IRI predicate and a constant IRI or literal object.
  - **The choice:** each such pattern's length is its `po` counter. A pattern at most `query.join.mergeratio` times the shortest is merged; the others are looked up for the merge's rows. The merge becomes the chain's driver, a `SubjectMergeJoin` node, so batched joins and entity chains above it work as before. RDF4J's own experimental merge join is not used (SCALE-STUDY.md 6.10).
  - **Defaults:** the ratio is unset by default, and `RyaSailFactory` then takes the store's `Capabilities.lookupCost()`: 35 on Accumulo, 20 on HBase, 8 on RocksDB, each measured on the join benchmark. Endpoint `tripatha.join-merge-ratio`; 0 turns merges off.
  - **Never merge without counters**, with a dataset or `query.limit`, or with the hashed row layout: its `po` rows aren't sorted by subject.
  - **`SubjectMergeStep`** reads subjects only (`RyaStoreQueryEngine.subjects`: each cell's subject bytes, no statement decoding) and compares them as unsigned bytes, which is the stored UTF-8 order; `String.compareTo` is not. It emits one row per combination of matching statements (graphs, labels), as the nested loop does. When the subject is already bound, as under an OPTIONAL, it runs the plain nested loop.
  - **Slices** (O24, `query.join.mergeslices`): the lists are cut at `spo`'s split points (`TableAdmin.splitRows`; RocksDB has none, so it uses the hints `addSplits` records or its SST files' first rows) and each slice is intersected on a daemon thread. Open every scan on the query thread (the trace is a `ThreadLocal`), and let the thread that reads a scan close it: RocksDB's native scanners must not be closed while another thread reads them. When lookups follow the merge (a join's or OPTIONAL's left side), slices are emitted in subject order, each through a queue of its own, so the lookups read nearby rows and the order doesn't depend on the slicing. Otherwise every slice feeds one queue (`FanIn`): emitted in order, a later slice gets only its queue's few thousand matches ahead, and at 100M triples 4 slices were barely faster than 1.
  - **A pattern on its own** (O7a, `query.join.mergesingle`, default 10,000; endpoint `tripatha.join-merge-single`): after the chains, a star pattern evaluated once per query (only unary operators, unions and left sides of joins, OPTIONALs and MINUS above it, and no shorter `LIMIT`) whose `po` counter is at least that long becomes a `SubjectMergeJoin` of one list, so it is read as subjects in slices instead of statements decoded on the query thread. Its scope, if it has one (a `UNION` arm), moves to the merge. The variable-object shape (`?s :p ?o`, O7b) is not done.
  - Run the ITs with `-Dtripatha.test.mergeRatio=1000000` to merge every star in every test, and with `-Dtripatha.test.mergeSingle=1` to make every star pattern on its own a merge; `SubjectMergeIT` compares merges on and off.
- **Search:** `text:matches` (`TextMatchesFunction`, registered in `META-INF/services`) and RDF4J's `geof:` functions always evaluate exactly.
  - `TextQueryValidator` (always on) rejects malformed constant text queries.
  - `IndexSearchOptimizer`, run after inference and before join ordering, swaps the statement patterns those filters cover for `IndexedStatementPattern`s. It leaves the filter in place.
  - `RyaEvaluationStrategy` runs those patterns with RDF4J's own `StatementPatternQueryEvaluationStep` over an `IndexTripleSource`. That source uses `IndexSearcher` when subject and object are unbound, and otherwise defers to the store.
  - `IndexSearcher` resolves every hit against spo with the query's conf, so the index can only cost time, never change results.
- **Triple terms** (ARCH.md 12.7): RDF4J parses a triple term in a pattern as a `TripleRef` joined with the statement pattern that uses its variable; annotations and reified triples add an `rdf:reifies` pattern.
  - `TripleTermOptimizer.fold` (after projection removal) turns all-constant `TripleRef`s into a one-row `BindingSetAssignment`; `order` (right after `QueryJoinOptimizer`) puts each remaining `TripleRef` just after the pattern that binds its variable.
  - `TripleRefStep` unifies a bound term in memory, and otherwise asks `StoreTripleSource.tripleTerms`. RDF4J's own step lists the whole store and casts subjects to `Resource`.
  - `TripleTermRangeSource` makes a statement pattern whose object is a term with a constant subject read only that prefix range. The `TripleRef` still checks every result.
  - Run `TripleTermIT` on every backend, and with the batch-size and index switches above, after touching any of this.
- **`STRSTARTS` as a prefix range** (`ObjectPrefixSource`, ARCH.md 12.8):
  - **When:** a pattern `?s <p> ?o` (or `?s ?p ?o`) under joins and filters only, with a filter conjunct `STRSTARTS(?o, "constant")`.
  - **What it does:** the pattern reads only the objects starting with the prefix, as a `RyaAnyTypeRange` (no object-type check) on `po` or `osp`. The filter stays, and `query.prefixranges` turns this off.
  - **Never extend it to `STR(?o)`:** numbers, dates and booleans are stored in their own encodings, outside the text range.
- **Comparisons as value ranges** (O14, ARCH.md 12.9): `?s <p> ?o FILTER(?o > 60)` reads only the objects whose stored data lies in the allowed range, one range of `po` per datatype of `p`'s objects. The filter stays.
  - **Where:** `ValueRangeOptimizer` (after the index search, before join ordering) turns a plain pattern with a variable subject, an IRI predicate and the compared object into a `ValueRangePattern`. The comparisons are `<`, `<=`, `>`, `>=`, `=` with a constant number or `xsd:dateTime`, in conjuncts of a filter above the pattern (through joins, unions, the left of OPTIONAL and MINUS, as `IndexSearchOptimizer`).
  - **When:** the store's markers are complete (flagged) and every datatype they report, under the query's labels, is `xsd:int`, `short`, `long`, `integer`, `double`, `float` (with numeric constants) or `dateTime` (with date-time constants). `query.valueranges` turns it off; never with `query.limit`, the hashed layout or row regexes.
  - **Bounds** (`ValueRanges`) are supersets on purpose: widened past RDF4J's float and double rounding, open past `INF` to keep NaN (RDF4J's `Double.compare` puts it above every number), and a second either side of a date-time. `xsd:byte` doesn't sort like its values, and a range open at both ends costs a whole scan, so either means no narrowing.
  - **Estimate** (O25): a pattern in a join has its ranges counted, cells only, under the query's labels (`RyaStoreQueryEngine.countValueRanges`), up to the estimate of the shortest other pattern of the join, and at most `query.valueranges.count` (1,000,000). Below the cap it is estimated at its count; at the cap as if unnarrowed (at least the cap): it is at least as long as another pattern, so it wouldn't drive. A fixed cap of 10,000 misplanned at 100M triples. A pattern on its own isn't counted, and a ceiling of 0 falls back to a tenth of the predicate.
  - **Tests:** `ValueRangesTest` checks the bounds against RDF4J's own comparisons; `ValueRangeIT` compares every query with the setting on and off, with no count, a cap of 3 and the default. Run both after touching any of this.
- **Inference nodes:** `RyaEvaluationStrategy.prepare(StatementPattern)` handles the two node types inference produces. `FixedStatementPattern` is matched from in-memory ontology statements; `TransitivePropertySP` goes through `InferenceEngine.findTransitiveProperty`.
- **`InferenceEngine`:** loads the ontology into memory (`ValueGraph` for the subClassOf/subPropertyOf hierarchies) and reloads it on a timer. Ontology changes are invisible until the next `refreshGraph()`; tests call it explicitly.
- **Wiring:** `RyaSailFactory` builds DAO + stats + inference + sail from a `Store` and a `StoreRdfConfiguration`. The caller owns the store.
- **Approximate counts** (O8, SCALE-STUDY.md 4.24): `ApproxCountOptimizer`, run just before inference, replaces `?g stats:approxSize ?n`, `?c stats:approxInstances ?n` and `?p stats:approxTriples ?n` patterns with a `FixedStatementPattern` built from `GraphSizes`. A constant subject reads one counter row.
  - **Class sizes** (`classSizes`): `rdf:type`'s all-graphs `po` counters, as stored (no inference).
  - **Predicate sizes** (`predicateSizes`): the all-graphs `p` counters; a variable predicate uses the predicate list below.
- **Graph sizes:**
  - `GraphSizes` sums each graph's eval `p` counters (qualifier = graph), for graphs that still have a marker.
  - It finds the predicates with a skip scan of `po` (one seek each) and keeps the list 5 minutes per set of auths.
  - Don't scan eval by column family instead: without a locality group that reads the whole table.

### Endpoint (`tripatha.sparql`)

- `SparqlController` implements the SPARQL Protocol at `/sparql` for SPARQL 1.1 and 1.2, with content negotiation in `ContentNegotiation` and errors mapped in `SparqlExceptionHandler`.
- **RDF 1.2 output:** `BlankNodeOutput` recurses into triple terms. SELECT results in JSON go through `DirectionJsonWriter` (`"its:dir": "rtl"`; RDF4J 6.1 writes `"--rtl"`, which its own reader rejects). RDF4J's TSV reader can't read a nested triple term back, and JSON-LD writes triple terms as `urn:rdf4j:tripleTerm:` IRIs.
- Settings are `RyaProperties` (`tripatha.*` in `application.yaml`). `tripatha.backend` picks the store (`RyaStoreConfiguration`); `tripatha.hbase.*` configures HBase (`conf[key]` for client settings), and `tripatha.rocksdb.path` is the directory of a RocksDB store. On HBase the endpoint refuses to start when its account can't read a label of `tripatha.sparql.authorizations` (their canaries).
- A request's `timeout=` (seconds) replaces `tripatha.sparql.query-timeout`, up to `tripatha.sparql.max-query-timeout`; the query page sends it from its Timeout field.
- **Tracing:** `trace=<id>` streams the request's storage operations as Server-Sent Events on `/sparql/trace/<id>` (`TraceController`, `TraceHub`), shown by `ui/tripatha-trace.js`.
  - Recording lives in `tripatha.store`'s `trace` package, and a `ThreadLocal` scope collects the events (see Backends for how each backend reports).
  - New code that reads should open `StoreTrace.reason(() -> "…")` around the read, so traces say why it scans.
  - A traced query must run exactly like an untraced one: never turn on RDF4J's result-size or time tracking for it (that disables batched joins). `QueryTraceIT` checks this.
  - Always close the scope in a `finally`: server threads are pooled.
- **Query page** (`src/main/resources/static`): `index.html` plus `ui/` (our code: `tripatha-ui.js` sets up YASGUI on `sparql`, `tripatha-map.js` is the Map result tab, `wkt.js` turns WKT into GeoJSON, `tripatha-sparql12.js` adds SPARQL 1.2 editing and RDF 1.2 results).
  - `tripatha-sparql12.js` replaces `Yasqe.prototype.checkSyntax`, YASR's response parser (`getParserFromContentType`, reached through a stand-in response) and the table plugin's `getCellContent`/`formatLiteral`. It must load before `tripatha-ui.js` creates YASGUI. A YASGUI upgrade has to recheck these hooks.
  - Graph results are requested as Turtle (set in `queryBefore`). Only our N-Triples 1.2 reader understands triple terms, so a SPARQL 1.2 query is requested as N-Triples, and a query whose Turtle result starts with RDF4J's `@version "1.2"` line is run once more as N-Triples (`queryResponse`).
  - CodeMirror overlays can't keep state, so the overlay's tokenizer starts fresh on each line.
  - Third-party files go to `static/vendor` at build time. The `maven-antrun-plugin` execution in `tripatha.sparql/pom.xml` downloads pinned npm tarballs into `~/.m2/repository/.cache/tripatha-ui` and checks their SHA-512.
  - To upgrade one, change its `*.version` and `*.sha512` properties (the hex of npm's `integrity`), and regenerate `static/vendor/THIRD-PARTY-NOTICES.txt`.
  - `SparqlUiIT` checks that every asset is served. JavaScript isn't tested in the build; check UI changes in a browser.
- **Launch wizard:** `configure.sh` (bash 3.2, so macOS's stock bash works) writes a launch script.
  - Settings go in as `--tripatha.*` arguments. Spring's environment-variable form of a dashed name drops the dash (`TRIPATHA_ACCUMULO_CLIENTPROPERTIES`), so arguments are less error-prone.
  - Only the password travels in the environment (`TRIPATHA_ACCUMULO_PASSWORD`). It is read when the script starts and never written. HBase needs none (simple authentication or Kerberos).
  - To test it, pipe answers in (one per line) or use `--defaults`, then run `bash -n` on the output.
- **No backend imports:** `RyaStoreConfiguration` builds each backend's settings and calls `Stores.open`, so the endpoint compiles without any backend (they are runtime dependencies). Keep it that way: `tripatha.standalone` leaves Accumulo and HBase out. A backend that can't refuse a read with unheld labels reports them through `StoreAccess.unreadableLabels`, which the endpoint checks at start-up.
- **Standalone and native** (`tripatha.standalone`): the endpoint's `lib` jar plus `tripatha.rocksdb`, repackaged as an executable jar; `-Pnative` runs Spring Boot's ahead-of-time processing and GraalVM's `native-image` (`target/tripatha`).
  - Reachability metadata is in `src/main/resources/META-INF/native-image/org.tripatha/traced/`. Don't put it under `org.tripatha/tripatha.standalone`: Spring's generated file has that path and replaces it.
  - It was collected with the tracing agent (`java -agentlib:native-image-agent=config-output-dir=DIR -jar …`) while `smoke-test.sh` ran against the jar. After upgrading RDF4J, Spring Boot or RocksDB, or adding a result format or a function, run that again, merge the result, rebuild and run `smoke-test.sh` against the executable. The Java ITs can't start it.
  - RocksDB's library is embedded as a resource per platform (the `librocksdbjni-*` globs) and unpacked to the temporary directory at start-up.
  - **Its heap:** native-image's Serial collector sizes its young generation from the minimum heap. With no `-Xms` it stays at about 100 MB and collects every few tens of milliseconds on large queries (38 % of WatDiv C3's time). So run a server with `-Xms` as well as `-Xmx` (SCALE-STUDY.md 4.15). The image has no fixed default, so small containers keep working.
  - **`build-optimized.sh`** builds it with profile-guided optimization, which needs Oracle GraalVM (GraalVM Community, used by CI and the Dockerfile, has none, and its `-O3` is its `-O2`). It loads a small join-benchmark store (`--triples 1M`, kept in `target/pgo`), trains an instrumented build on that suite through CompareBench, then builds with `--pgo`. Each build's log must show the PGO setting it was given. Never train on WatDiv: `compare.sh` measures it. Don't ship `-march=native` either: alone it gained nothing, and it builds for the build machine's CPU only (on top of the profile it took C3 from 599 to 503 ms, but the comparison's other engines are generic builds).
  - The Dockerfile's last stage is picked by the `TRIPATHA_BACKEND` build argument: the JVM image for accumulo and hbase, the native one (built in a GraalVM stage, run on Debian) for rocksdb. The run-time glibc must be at least the build image's.
- `DevServer`, under test sources, runs the endpoint on a throwaway in-process cluster (`mvn -pl tripatha.sparql spring-boot:test-run -Dspring-boot.run.main-class=org.tripatha.sparql.DevServer`; add `-Dspring-boot.run.jvmArguments=-Dtripatha.test.backend=hbase` for HBase, or `"-Dtripatha.test.backend=rocksdb -Dtripatha.test.rocksdbPath=DIR"` for a RocksDB store that keeps its data in `DIR`). The Docker image runs it for accumulo and hbase.

## Gotchas

- **RDF4J 6 `Var` nodes may have only one parent** (assertion in `Var.setParentNode`; tests run with `-ea`). When building new query nodes from existing variables, clone them: the inference visitors use `AbstractInferVisitor.c(var)`.
- **A triple term must never be a constant `Var` in a `StatementPattern`:** RDF4J's `StatementPatternQueryEvaluationStep` returns that same `Var` for it and trips the one-parent assertion. Bind it through a `BindingSetAssignment` row, as `TripleTermOptimizer.fold` does. Query bindings set from outside with a triple term value hit the same assertion under `-ea`.
- **Eval counters are keyed on a value's data without its type,** so a triple term and a string with the same data share a counter.
- **`null` context means different things.**
  - In a Tripatha `RyaStatement` pattern: any graph.
  - In RDF4J: the default graph.
  - So default-graph lookups and deletes go through `StoreTripleSource` / `RyaDAO.delete(pattern, filter, conf)`, and `dropGraph` with a `null` element means the default graph (no graphs at all means everything).
- **Blank nodes** are stored, and returned by the sail, as IRIs in `RyaSchema.BNODE_NAMESPACE`. The inference engine casts these to `IRI` throughout, so don't change this in `RyaToRdfConversions` without reworking inference. The endpoint maps them back to real blank nodes only in its output (`BlankNodeOutput`).
- **Per-connection configuration:** each connection clones the store configuration. Set per-request auths or visibility (`conf.cv`) on `RdfCloudTripleStoreConnection.getConf()`, never on the store's shared configuration.
- **Exceptions:** `RyaDAOException` is unchecked, and RDF4J 6 iterations have no exception type parameter.
- **Writes are not transactional:** commit = flush, and rollback does nothing.
- **`tripatha.sparql` build quirks:** Failsafe is pointed at `target/classes` (the Boot repackage hides classes inside the jar), and `jcl-over-slf4j` is excluded because Spring 7 bundles commons-logging.
- **Index invariants.** Breaking any of these loses search results or leaves stale index entries.
  - The terms of a statement must depend only on what spo stores. `deleteMatches` recomputes them from the stored match.
  - Index puts and deletes use the statement's timestamp.
  - Changing `TextAnalyzer` or `GeoCells` rules means bumping `TextAnalyzer.VERSION` / `GeoCells.DEFINITION`, so existing indexes require a rebuild.
  - Don't add a `wktLiteral` type resolver: it would change the stored object encoding.
  - The index tables follow `dropGraph`'s auth-scoped deletes, because cf = graph.
  - RDF4J's LuceneSail is not usable here: it needs a NotifyingSail and ignores visibility labels.
- **DAO init and permissions:** `init()` must not write when the store is already set up (an unchanged index state is not rewritten), and `ensureSettings` skips the stats-combiner check when the user may not read table settings (that needs ALTER_TABLE on Accumulo). Read-only users, such as an endpoint account, must be able to open a store.
- **HBase labels differ from Accumulo's** (BACKENDS-STUDY.md 4.2): superusers see every cell, an empty set means every held label, unheld labels are dropped silently, unregistered ones are refused on write, and `addLabels`/`setAuths` report failures inside the response. Never compute "my labels" with `getAuths` (empty for normal accounts): use `Auths.ALL_HELD`. Labels are only enforced with `hbase.security.authorization=true`.
- **HBase counters in coprocessor mode keep every version** until a flush or major compaction folds them; readers must add up every cell they get for a counter (the DAO and `GraphSizes` do). Puts take shared row locks, so `CounterObserver` must stamp timestamps atomically (`CounterIT` hammers this).
- **Loader:** run `prepare` before any `load`, with the same dataset and index options (`prepare` prints them). The endpoint must use the same table prefix and index settings. Counters can drift only for blocks in flight when a load fails, since a resume writes them again.
- **License headers.**
  - Files that came from Apache Rya keep their ASF header unchanged, including heavily rewritten ones. The Apache License requires it.
  - New files get the standard Apache 2.0 header from the appendix of `LICENSE` (`Copyright 2026 David Greco`), not the ASF one.
- **Attribution:** keep `NOTICE` and the README's "derived from Apache Rya" line. Don't call the project "Apache Rya": that name is an ASF trademark.
